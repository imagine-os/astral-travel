# Make discovery contagious

Astral Travel should earn adoption by making a valuable idea easy to understand, easy to try, and easy to explain to somebody else.

The launch goal is not a claim to be the most downloaded repository. GitHub does not provide a universal repository download ranking. Stars, clones, package downloads, active workspaces, and returning users measure different things.

## The launch promise

**Your second brain. Beyond remembering.**

Supporting sentence:

> Keep your sources. Discover connections. Explore possibilities. Bring better ideas back.

The first public story is a working local foundation for those behaviors. Describe what is shipped before describing where it can go.

## The story people can retell

**“Three ordinary notes became one useful question.”**

Use a fictional creative studio. It has a customer request for easier handoffs, a support note about permissions, and a roadmap idea for shared spaces. Show the sources, suggest the connection, and ask whether the real need is simpler collaboration. Let the viewer inspect the evidence and explore two possible responses.

End with the question or decision, not a cloud of glowing nodes. The value is an insight someone can act on.

### A 45-second walkthrough

| Time | What the viewer sees | What they understand |
| --- | --- | --- |
| 0–7 seconds | Three short notes | “I have information like this.” |
| 7–17 seconds | A proposed connection | “These notes might belong together.” |
| 17–27 seconds | Sources opened from the suggestion | “I can check why.” |
| 27–37 seconds | Grounded and speculative possibilities kept apart | “I can explore without confusing imagination with evidence.” |
| 37–45 seconds | A useful next step and a link to try it | “I know what I could use this for.” |

Record the real interface. If a desired sequence is not implemented yet, make it a clearly labeled concept film instead of presenting it as product behavior.

## The adoption loop

1. A short, understandable demo attracts a relevant person.
2. The browser lab gives them a first useful experience without setup.
3. The source trail builds trust in the result.
4. A fictional or redacted export makes the workflow easy to share.
5. Local setup, five stdio MCP tools, and a small codebase make experimentation possible.
6. Real workflow reports and contributions improve the next release.

The distribution object should be a **useful story with its evidence**, not a star request pasted into every channel.

## First distribution experiments

These are proposed experiments, not claims about campaigns already run.

- **Developers:** a technical walkthrough of raw versus derived data, provenance, a minimal local engine, and the working local MCP setup.
- **Vibecoders:** a “build your own memory workflow” tutorial using a small fictional dataset.
- **Business owners:** a three-note customer discovery demonstration with ordinary language.
- **Researchers:** a source-first exploration showing how to inspect support and uncertainty.
- **Creative people:** grounded and speculative scenarios shown side by side, with the boundary visible.

Publish where each audience already discusses these problems. Participate in the conversation, answer limitations honestly, and follow the community's self-promotion rules. Never buy stars or manufacture testimonials.

The MCP demonstration should show a real stdio client using the [five documented tools](mcp.md). Present local setup accurately: the website URL is not a remote MCP endpoint, and browser data is separate from the CLI/MCP workspace. Show an explicit accept/reject decision before an agent applies a dream review.

## Measure the useful part

The alpha has no hosted analytics backend. This is a measurement plan for later implementation or voluntary user studies, not a statement that these events are currently collected.

| Metric | Definition | Why it matters |
| --- | --- | --- |
| Time to first insight | Median time from a first visit to a user identifying a useful connection | Tests whether the product becomes useful quickly. |
| First-session activation | People who ingest or inspect sources, review a connection, and inspect its provenance | Distinguishes curiosity from a completed workflow. |
| Return use | Activated people who repeat a useful workflow on a later day | Tests durable value. |
| Retrieval success | Queries for which a relevant source appears in the expected results | Measures whether the foundation works. |
| Suggestion usefulness | Reviewed suggestions marked useful, with reasons | Improves quality beyond volume. |
| Provenance completion | Accepted ideas with inspectable supporting sources | Checks whether trust survives growth. |
| Setup success | Fresh local walkthroughs completed without maintainer help | Measures developer accessibility. |
| Contribution conversion | First useful reports or contributions that receive a response and reach resolution | Measures community health. |

Track stars as discovery context, not as the success metric. A true “star-to-activation” rate requires opt-in identity linkage; dividing anonymous activations by star growth is only an aggregate proxy and should be labeled as such. Avoid quietly identifying users to manufacture that number.

## What deserves deeper study

| Topic | The question to investigate |
| --- | --- |
| Memory consolidation | Which summaries preserve useful detail, uncertainty, and exceptions? |
| Temporal knowledge | How should beliefs change when sources become stale or contradict each other? |
| Ontology evolution | How can personal labels converge without forcing everyone into one taxonomy? |
| Retrieval evaluation | Can the system find relevant evidence across realistic messy corpora? |
| Dream quality | Which unexpected connections lead to real decisions instead of noise? |
| Simulation discipline | How do assumptions, constraints, and alternate worlds stay explicit? |
| Improvement loops | What evidence justifies a change, and how is it reviewed and reversed? |
| Procedural memory | Can a successful workflow become a reusable skill with a history? |
| Attention and forgetting | What should be resurfaced, archived, consolidated, or deleted? |
| Multi-person memory | Whose knowledge is this, who may see it, and who can revise it? |
| Interoperability | Can a user leave with sources, relationships, and history intact? |
| Media-scale architecture | Can a small knowledge index reference enormous media collections efficiently? |
| Spatial navigation | When does a room or map improve recall and orientation over search or a list? |
| Accessibility and input | Can the same intent work through keyboard, pointer, touch, voice, and controller? |

## The next release should prove one thing

Choose a small, measurable promise per release. Examples include “find the right source more reliably,” “explain why a connection was suggested,” or “recognize a stale claim without losing its history.”

A launch can create attention. Repeated useful releases create a project people recommend.
